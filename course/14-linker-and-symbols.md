# 14 — Objects, symbols and the linker

Until now, many examples looked like one source file becoming one program.

Real programs are usually not built that way.

M7 splits a tiny program into two assembly modules:

```text
main.s
  reset
  JSR double_a
        |
        | unresolved symbol in main.o
        v
math.s
  double_a
```

The assembler can create each object independently. The linker decides where the final symbols live and resolves the cross-module reference.

## 1. Assemble, do not link

The lab uses LLVM-MOS's standalone assembler:

```sh
llvm-mc -triple mos -mcpu=mosw65c02 --filetype=obj \
  examples/asm/m7/main.s -o main.o
```

Do the same for `math.s`.

An object file is not the EEPROM image.

It contains code/data sections plus metadata that lets later tools understand symbols and relocations.

## 2. Inspect before linking

Ask:

- Which symbols are defined?
- Which symbols are still undefined?
- Which sections exist?
- Where is the reference to `double_a` recorded?

Use `llvm-readelf`, `llvm-nm` and `llvm-objdump`.

Do this **before** linking so you can see what the linker still has to solve.

## 3. The linker script is part of the machine

`toolchain/m7/link.ld` says that executable content belongs in the Edu65xx ROM region:

```text
$C000-$FFFF
```

It also pins the vector section at:

```text
$FFFA
```

This is not merely a file-format choice. It connects software layout directly to the hardware memory map.

If the linker puts RESET code at the wrong address, perfect C or assembly code still cannot boot the machine.

## 4. Link

The lab invokes LLD in GNU-compatible mode and writes a map file.

The outputs include:

```text
program.elf
program.map
symbols.txt
readelf.txt
disassembly.txt
program.bin
```

The ELF file is for tools and understanding.

The 16 KiB binary is the ROM-shaped output.

## 5. Follow one symbol

Find `double_a` in:

1. `math.o`
2. the relocation/reference from `main.o`
3. `program.map`
4. `symbols.txt`
5. final disassembly

Then find the bytes of the final `JSR`.

The source says:

```asm
jsr double_a
```

The final machine code must contain a concrete 16-bit target address.

That address did not need to be known when `main.s` was assembled.

That is the linker's job.

## 6. Vectors are linked data

The vector module is deliberately not generated by a post-build patcher.

The source contains three words in a dedicated `.vectors` section and the linker places that section at `$FFFA`.

Inspect the last six bytes of `program.bin` and connect them to:

- NMI
- RESET
- IRQ/BRK

## Lab questions

1. What address did `reset` receive?
2. What address did `double_a` receive?
3. What bytes encode `JSR double_a`?
4. Why can `main.o` exist before `double_a` has a final address?
5. Why is `program.elf` more useful for debugging than a raw ROM image?
6. Why is the raw 16 KiB image still useful?

## Reproduce

With the pinned LLVM-MOS SDK on PATH:

```sh
scripts/build-linker-lab.sh
```

Do not memorize the addresses printed by one build. Inspect them. Changing section contents can move symbols while preserving the same source-level relationship.
